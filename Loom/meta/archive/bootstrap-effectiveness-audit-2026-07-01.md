# Poyi 自举有效性评估报告

> **核心问题**：一个新 Agent 能不能通过 AGENTS.md 完成全量自举，了解用户和工作流，并在工作后及时更新所有相关文件不遗漏？
>
> **简短结论**：**能完成 70-80% 的自举，了解用户和工作流的大部分内容，但做不到"不遗漏"地更新所有文件。**
>
> **整体评分**：**72/100**

---

## 一、三维度评估总览

| 维度 | 评分 | 说明 |
|---|---|---|
| 了解用户 | 85/100 | 用户画像非常详细，Persona + profile 双轨制覆盖全面 |
| 了解工作流 | 75/100 | 核心工作流有文档，但很多细节需要深入挖掘 |
| 文件更新不遗漏 | 60/100 | propagation-map 覆盖了主要场景，但有明显盲区 |
| **综合自举有效性** | **72/100** | 骨架完整，细节待补 |

## 二、了解用户：85/100 — 非常全面

### ✅ 新 Agent 能了解到的

#### 2.1 内在画像（Persona.md）
- **基本信息**：姓名、学校、专业、GPA、保研目标、城市、设备
- **核心身份标签**：北屿大学工科生、示例车队、创作者、音乐爱好者、AI重度协作者
- **核心目标**：学业/Samplelab品牌/音乐创作三线并行
- **技能图谱**：工程技术 + 创作能力，带熟练度评估
- **工作风格**：优点 + Antigravity编程习惯 + 弱点
- **沟通风格**：直接、有边界、接受不确定性、成长型
- **已知偏好**：中文优先笔记、命名规范、考前冻结、周日休息
- **风险意识**：4大风险等级和对策
- **日记洞察**：写作习惯、情绪模式、核心价值观
- **长期愿景**：差异化定位的清晰描述

#### 2.2 操作画像（profile SKILL.md）
- **组织与角色**：7个组织+角色+对应群名
- **AI工具与工作流**：Marvis/Antigravity/Hermes分工，模型切换策略
- **技术环境**：10+种工具和环境的配置状态
- **D盘顶层结构**：9个目录的清晰划分
- **工作偏好**：preview-before-commit、保守清理、直接行动
- **群聊username速查表**：10个群的精确ID

#### 2.3 动态信息
- **对话消化摘要**：每天的summary.md + knowledge.json + preferences.json
- **项目状态**：7个项目的plan.md + progress.md

### ⚠️ 了解不到/需要深挖的

1. **具体项目的当前进展和阻塞点** — 需要深入每个项目的progress.md
2. **具体的知识体系和笔记内容** — 需要深入Vault/notes/各领域
3. **隐性的工作习惯和偏好细节** — 需要从对话历史中慢慢积累
4. **人际关系网络** — 只有辅导员和组织，没有更详细的人际信息

## 三、了解工作流：75/100 — 骨架完整，细节需挖

### ✅ 新 Agent 能了解到的

#### 3.1 系统架构
- **双区划分**：Vault（人+AI协作区）+ Loom（AI专属工作区）
- **23个技能体系**：13个用户技能 + 10个Wiki核心技能
- **技能依赖关系图**：清晰的依赖链
- **自举协议**：8步接管流程

#### 3.2 核心工作流
- **filesystem技能**：跨平台文件系统规范，有详细的决策树和陷阱清单
- **inbox技能**：三模块（digest/radar/scout）信息中枢，有明确的边界和推送节奏
- **profile技能**：用户画像的更新机制和触发条件
- **Wiki工作流**：ingest/query/lint/save/research 五模块
- **知识传播矩阵**：4类信源 → 落点文件的映射

#### 3.3 规范与约束
- **命名规范**：kebab-case强制，≤2词，禁下划线
- **Vault规则**：禁止指向Loom的链接、禁止AI元注释
- **维护规则**：技能变更、结构变更后的更新要求

### ⚠️ 了解不到/需要深挖的

1. **大部分技能的内部工作流细节** — 自举协议只要求读INDEX.md，不要求读每个技能的SKILL.md
2. **跨技能的协同工作流** — 没有总览文档说明多个技能如何配合工作
3. **日常使用的具体节奏和习惯** — 没有"一天的工作流"总览
4. **异常处理流程** — 出问题了怎么办？没有故障排查指南
5. **很多隐性约定** — 比如"为什么要这样设计"的背景知识

## 四、文件更新不遗漏：60/100 — 有明显盲区

### ✅ propagation-map 覆盖的场景

| 信源类型 | 覆盖的落点数量 | 示例 |
|---|---|---|
| 编程对话 | 7类 | 技术选型→plan.md+profile；架构设计→plan.md+progress.md |
| 日常聊天 | 8类 | 项目想法→plan.md；生活事件→Persona.md；待办→progress.md+inbox |
| Skill自身演进 | 5类 | 新增skill→INDEX.md+profile+所有引用处 |
| 项目物理变更 | 4类 | 新建项目→INDEX.md+plan.md+progress.md |

### 🔴 propagation-map 没有覆盖的盲区（8大场景）

#### 盲区1：笔记更新
- **场景**：用户写了新笔记，或整理了旧笔记
- **问题**：propagation-map完全没有提到笔记更新后需要同步更新哪些文件
- **可能遗漏的文件**：
  - 对应领域的wiki页面
  - 项目相关的笔记是否需要同步到项目文档
  - 技能相关的笔记是否需要更新技能文档

#### 盲区2：Wiki知识库更新
- **场景**：ingest了新的资料，或save了对话到wiki
- **问题**：没有说明wiki更新后需要同步更新哪些索引和元文件
- **可能遗漏的文件**：
  - `wiki/index.md` — 全局目录
  - `wiki/hot.md` — 热缓存
  - `wiki/log.md` — 操作日志
  - `wiki/overview.md` — 知识图谱概览
  - 对应分类的_index.md

#### 盲区3：英语学习痕迹
- **场景**：用户学了新的英语表达
- **问题**：propagation-map完全没有提到英语学习场景
- **可能遗漏的文件**：
  - `Loom/wiki/english-data/` 下的对应文件
  - `Vault/notes/语言 Language/` 下的笔记
  - review技能中的英语掌握度追踪

#### 盲区4：复习/掌握度追踪
- **场景**：用户进行了复习自测
- **问题**：propagation-map完全没有提到复习场景
- **可能遗漏的文件**：
  - `Loom/wiki/review/<subject>/mastery.json`
  - `Loom/wiki/review/<subject>/session-log.md`
  - 对应学科的笔记是否需要补充

#### 盲区5：日记/个人记录
- **场景**：用户写了新日记
- **问题**：没有说明日记更新后需要同步更新什么
- **可能遗漏的文件**：
  - Persona.md中的情绪模式、核心价值观是否需要更新
  - profile中的基本信息是否有变化
  - 日记中提到的项目进展是否需要同步到项目文档

#### 盲区6：对话归档
- **场景**：对话消化归档后
- **问题**：没有说明对话归档后需要更新哪些文件
- **可能遗漏的文件**：
  - wiki中的相关知识页面
  - profile中的偏好和工作流
  - Persona中的用户画像
  - 项目进度

#### 盲区7：inbox三模块的具体落点模糊
- **问题**：propagation-map中只写了"inbox skill"，但inbox有三个子模块（digest/radar/scout），每个模块的数据文件都不一样
- **影响**：新Agent不知道具体该更新inbox下的哪个文件

#### 盲区8：缺少连锁更新机制
- **问题**：没有说明A文件更新后，依赖A的B文件是否也需要更新
- **示例**：
  - 更新了profile的技术栈 → 是否需要同步更新所有相关项目的plan.md？
  - 更新了Persona的技能评分 → 是否需要同步更新profile？
  - 重命名了一个skill → 是否需要检查所有引用该skill的地方？

## 五、自举协议本身的问题

### 🔴 问题1：第五步断点
- **问题**：自举协议第五步要求检查`Loom/chat-logs/marvis/`目录，但该目录不存在
- **影响**：严格按协议执行的新Agent会在这里卡住
- **严重度**：高

### 🟡 问题2：第四步信息不足
- **问题**：自举协议第四步只要求读`wiki/index.md`，但index.md几乎是空的
- **影响**：新Agent对Wiki系统的了解非常有限
- **严重度**：中

### 🟡 问题3：缺少"深入到什么程度"的指导
- **问题**：自举协议说"按需深入"，但没有说明什么情况下需要深入到什么程度
- **影响**：新Agent可能读得不够，也可能读得太多浪费时间
- **严重度**：中

### 🟢 问题4：缺少验证环节
- **问题**：自举完成后，没有一个"自举完成检查清单"来确认是否真的了解了所有重要信息
- **影响**：新Agent可能以为自己了解了，但实际遗漏了关键信息
- **严重度**：低

## 六、改进建议

### P0（立即修复）
1. **修复自举协议第五步断点** — 要么创建marvis目录，要么更新协议描述
2. **在propagation-map中补充8大盲区** — 特别是笔记更新、wiki更新、英语学习、复习追踪

### P1（近期改进）
3. **给propagation-map的条目增加具体文件名** — 不要只写"inbox skill"，要写清楚是哪个文件
4. **增加"自举完成检查清单"** — 确保新Agent没有遗漏关键信息
5. **补充连锁更新规则** — 说明什么情况下需要连锁更新哪些文件

### P2（长期完善）
6. **写一份"日常工作流总览"** — 一天中各个时间点通常做什么、用什么技能
7. **写一份"故障排查指南"** — 常见问题的处理方法
8. **增加"为什么这样设计"的背景知识** — 帮助新Agent理解设计决策背后的原因

## 七、最终结论

**好消息**：Poyi系统的自举体系已经相当完善了。一个新Agent按照AGENTS.md的8步协议走一遍，确实能快速了解用户和系统的大致情况，快速上手工作。Persona + profile的双轨制用户画像设计得非常好，覆盖了内在特质和操作层面。

**坏消息**："更新所有相关文件不遗漏"这个目标目前还达不到。propagation-map只覆盖了最核心的4类场景，还有至少8个明显的盲区。一个尽责的新Agent可能会因为不知道该更新哪些文件而遗漏重要信息，或者因为过度谨慎而更新太多不必要的文件。

**建议**：把propagation-map从"4类信源"扩展到"8-10类信源"，补充笔记、wiki、英语、复习、日记、对话归档等场景，并给每个条目增加具体的文件名。这样文件更新的覆盖率应该能从60分提升到85分以上。
